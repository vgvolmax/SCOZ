# SCOZ — UI/UX Design

**Дата:** 2026-08-13  
**Статус:** нормативный UI/UX design для PR-планирования  
**Репозиторий:** `vgvolmax/SCOZ`

## 1. Назначение документа

Этот документ фиксирует пользовательскую архитектуру SCOZ на основании действующих продуктовых ТЗ и `Architecture Design`.

Он определяет:

- CJM;
- JTBD;
- информационную архитектуру;
- структуру основных экранов;
- правила progressive disclosure;
- обязательные loading / progress / success / partial / error / insufficient-data состояния;
- правила отображения benchmark и аналитических выводов;
- UX работы с импортом, источниками, конкурентами, запросами, кластерами и режимом «Разгон»;
- требования к обратной связи системы на каждое действие пользователя.

Этот документ не меняет продуктовую методологию. Он отвечает на вопрос:

> Как сделать сложную аналитику SCOZ понятной без необходимости разбираться во внутренней математике и всегда давать пользователю ясное понимание текущего состояния системы?

Следующий `PR Development Plan` должен учитывать этот документ наравне с продуктовым ТЗ и Architecture Design.

# 2. UX North Star

Главный принцип SCOZ:

> **Пользователь всегда понимает: где он находится, что сейчас анализируется, что система делает, какой результат получен и что мешает получить результат, если данных недостаточно.**

SCOZ не должен ощущаться как BI-конструктор и не должен заставлять пользователя собирать вывод самостоятельно из десятков таблиц.

Приоритет представления:

> **Ответ → причина → подтверждающие показатели → исходные данные.**

На каждом уровне система должна показывать ровно столько данных, сколько нужно для следующего решения.

Ключевой UX-критерий:

> после загрузки корректных данных пользователь должен за несколько секунд понять главный провал SKU и направление дальнейшего исследования.

Это не жёсткий performance SLA, а принцип информационной архитектуры.

# 3. Базовые UX-принципы

## 3.1. Никаких «тихих» действий

Любое действие, которое меняет состояние или требует ожидания, должно дать немедленную визуальную обратную связь.

Примеры:

- файл выбран → UI сразу показывает, что файл принят в обработку;
- импорт начат → видно текущий этап;
- benchmark-группа изменена → видно, что benchmark пересчитывается;
- API синхронизируется → виден источник и стадия;
- запрос выбран → выбранный запрос визуально остаётся активным;
- данные отсутствуют → показывается не пустой блок, а причина;
- операция завершена частично → UI явно отличает partial success от полного успеха.

Не допускаются сценарии:

- пользователь нажал кнопку и не понял, произошло ли что-то;
- spinner без пояснения висит длительное время;
- ошибка исчезает в console/log;
- данные изменились без указания, что именно обновилось;
- экран показывает старые данные так, будто они свежие.

## 3.2. Контекст всегда видим

Пользователь не должен помнить, какой объект он анализирует.

На аналитических экранах постоянно виден активный контекст:

- собственный SKU / товар;
- выбранный период;
- benchmark-группа;
- выбранный поисковый запрос, если применимо;
- выбранный кластер, если применимо;
- дата/свежесть данных;
- confidence / недостаточность данных там, где это влияет на вывод.

## 3.3. Progressive disclosure

Первый уровень показывает диагноз.

Второй — ключевые показатели, объясняющие диагноз.

Третий — конкретных конкурентов, распределение, P25/P75, дополнительные факторы и provenance.

Нельзя выводить все доступные поля Ozon на основной экран только потому, что они существуют.

## 3.4. Цвет не является единственным носителем смысла

Красный / жёлтый / зелёный используются как ускоритель чтения, но всегда сопровождаются:

- числом;
- текстовым статусом или иконкой;
- понятным направлением отклонения.

Пользователь должен понимать таблицу и без различения цветов.

## 3.5. Никакой ложной точности

Оценки режима «Разгон» показываются диапазонами.

Если данных недостаточно, вместо графика или прогнозного числа показывается `Недостаточно данных` и объяснение, чего именно не хватает.

Система должна визуально различать:

- **Факт** — напрямую наблюдаемое значение источника;
- **Расчёт** — детерминированная производная метрика;
- **Оценка** — модельный результат.

Не требуется постоянно показывать эти бейджи на каждом числе; они обязательны в детализации и в местах, где пользователь может принять оценку за факт.

# 4. Основные JTBD

## JTBD-1. Быстро диагностировать SKU

**Когда** продажи товара хуже ожиданий или конкурентов,  
**я хочу** открыть SKU и сразу увидеть главный источник отставания,  
**чтобы** не разбирать вручную несколько отчётов Ozon.

Ожидаемый ответ SCOZ:

> Продажи ниже benchmark преимущественно из-за трафика; конверсия находится около benchmark.

## JTBD-2. Найти поисковые запросы с реальным потенциалом

**Когда** карточка недополучает поисковый трафик,  
**я хочу** увидеть не просто список запросов, а приоритетные поисковые возможности,  
**чтобы** работать с запросами, где одновременно есть спрос, хороший интент и существенный visibility gap.

## JTBD-3. Понять географию проблемы

**Когда** SKU плохо стоит по важному запросу,  
**я хочу** увидеть разницу по кластерам и факторам ранжирования,  
**чтобы** отличить системную проблему карточки от локальной проблемы доставки или других кластерных факторов.

## JTBD-4. Отличить плохую карточку от плохого места

**Когда** абсолютная конверсия SKU ниже конкурентов,  
**я хочу** понять, нормальна ли эта конверсия для текущего места в выдаче,  
**чтобы** не менять карточку, если основное ограничение — позиция.

## JTBD-5. Понять, стоит ли разгонять товар рекламой

**Когда** SKU имеет нормальную позиционно-нормализованную конверсию, но стоит низко,  
**я хочу** оценить сценарии TOP-20 / TOP-10 / TOP-3 и диапазон ставки,  
**чтобы** решить, есть ли смысл временно увеличить рекламную поддержку.

## JTBD-6. Понять, закрепляется ли товар

**Когда** товар уже разгоняется,  
**я хочу** видеть, уменьшается ли ставка, требуемая для удержания сопоставимой позиции,  
**чтобы** понять, усиливается ли органическая опора товара.

## JTBD-7. Сформировать честную benchmark-группу

**Когда** SCOZ находит кандидатов в конкуренты,  
**я хочу** быстро увидеть их главные фото и основные признаки,  
**чтобы** выбрать только действительно сопоставимые товары и не загрязнять benchmark нерелевантными SKU.

## JTBD-8. Доверять данным и понимать состояние системы

**Когда** я загружаю отчёт или синхронизирую API,  
**я хочу** видеть, что именно происходит, какие данные обновились, какие строки не приняты и насколько свеж результат,  
**чтобы** не принимать решения на основе неполных или устаревших данных.

# 5. Пользовательская модель

SCOZ проектируется прежде всего для пользователя, который понимает бизнес маркетплейса, но не обязан знать внутреннюю структуру базы или методику каждого расчёта.

Основной пользователь:

- product / marketplace manager;
- бизнес-аналитик;
- коммерческий руководитель, которому нужен быстрый диагноз SKU.

Не требуется создавать разные role-based интерфейсы в первой версии.

Сложность регулируется progressive disclosure, а не отдельными ролями.

---

# 6. Информационная архитектура

Глобальная навигация должна быть короткой.

Рекомендуемая структура:

1. **Товары** — основной рабочий раздел;
2. **Данные** — импорты, синхронизация и история источников;
3. **Настройки** — ключи/подключения и технические настройки.

Не создавать отдельные глобальные разделы для:

- Benchmark;
- рекламы;
- Query Opportunity;
- кластеров.

Это контекст конкретного товара и должно жить внутри workspace SKU.

# 7. Главный объект интерфейса — Product Workspace

После выбора собственного товара пользователь попадает в единый workspace SKU.

## 7.1. Постоянный header товара

Header содержит:

- главное фото собственного товара, если доступно;
- название;
- Ozon SKU / offer ID при необходимости;
- активный период;
- свежесть основных данных;
- состояние benchmark-группы;
- общий data readiness.

Не перегружать header аналитикой.

## 7.2. Вкладки workspace

Рекомендуемые основные вкладки:

### `Диагностика`

Главный экран SKU.

### `Поиск`

Query Opportunity + кластерная heatmap.

### `Разгон`

Position-normalized CR, сценарии и organic-support trend.

### `Конкуренты`

Управление benchmark-группой.

Сырые данные и технический provenance не являются отдельной основной вкладкой; они открываются из деталей и раздела «Данные».

# 8. CJM — первый запуск

## Этап 1. Запуск

Пользователь запускает `start.bat`.

Ожидание пользователя:

> приложение должно открыться само, без терминальной магии и необходимости понимать runtime.

UX:

- bootstrap показывает понятный текстовый прогресс в launcher-окне;
- если это первый запуск, стадии названы человечески: `Подготовка приложения`, `Проверка компонентов`, `Запуск SCOZ`;
- технические детали доступны в логах, но не являются основным текстом;
- при повторном запуске не показывается ложная «установка».

Если запуск не удался, сообщение должно содержать:

- что произошло;
- можно ли повторить;
- где находится лог;
- что пользователь может сделать без разработчика.

## Этап 2. Первый экран приложения

Если данных нет, пользователь не должен попадать на пустой dashboard.

Показывается readiness-screen:

> Для анализа добавьте данные Ozon и выберите собственный товар.

Основные действия:

- `Загрузить отчёт`;
- `Настроить источник` — если API уже поддерживается.

Не требуется длинный onboarding wizard.

# 9. CJM — загрузка и обновление данных

## Цель

Пользователь хочет добавить новый snapshot и быть уверенным, что SCOZ корректно его понял.

## Поток

1. Пользователь выбирает файл.
2. SCOZ немедленно отображает имя файла и начинает проверку.
3. Автоматически определяется тип отчёта.
4. Показывается стадия обработки.
5. После импорта показывается результат.
6. Аналитика, затронутая новыми данными, пересчитывается.

## Обязательные стадии долгого импорта

Пример:

- `Читаем файл`;
- `Проверяем структуру`;
- `Нормализуем данные`;
- `Сохраняем snapshot`;
- `Обновляем аналитику`.

Процент показывается только если его можно посчитать честно.

Если точный progress неизвестен, показывается текущая стадия и elapsed time, но не декоративные `63%`.

## Результат импорта

Отображать:

- тип отчёта;
- период данных;
- импортировано записей;
- пропущено;
- предупреждения;
- дубликат / не дубликат;
- что именно стало доступно после импорта.

Пример:

> Импорт завершён: 1 248 записей добавлено, 3 пропущено. Обновлены товарные benchmark для 41 SKU.

При partial success статус должен быть `Импортировано с предупреждениями`, а не зелёное безусловное «Готово».

# 10. Универсальный Operation Feedback Contract

Любая операция длительнее мгновенного UI-изменения должна иметь явное состояние.

Минимальная state model:

- `IDLE`;
- `VALIDATING`;
- `RUNNING`;
- `PARTIAL_SUCCESS`;
- `SUCCESS`;
- `FAILED`;
- `CANCELLED`, если операция допускает отмену.

Для аналитического результата дополнительно:

- `STALE`;
- `INSUFFICIENT_DATA`.

## 10.1. Время реакции

- действие пользователя должно визуально подтверждаться практически сразу;
- при короткой операции достаточно локального loading state;
- при длительной операции нужен текст стадии;
- если операция может занимать много секунд, пользователь должен видеть, что процесс жив, и не должен гадать, зависло ли приложение.

## 10.2. Backend/API contract для долгих операций

Если операция не может быть надёжно выполнена в рамках короткого HTTP request, application/API слой должен поддерживать operation state.

Рекомендуемый DTO:

```text
OperationStatus
- id
- type
- state
- stage
- progress_current? / progress_total?
- human_message
- started_at
- updated_at
- retryable
- error_code?
```

UI не должен сам угадывать стадию обработки по таймерам.

# 11. CJM — формирование benchmark-группы

## Цель

Выбрать реальных конкурентов, а не весь TOP выдачи.

## Экран `Конкуренты`

Кандидаты показываются карточками или плотной grid-таблицей, где главное место занимает изображение.

Для каждого кандидата:

- главное фото;
- название;
- бренд;
- цена покупателя;
- SKU;
- из какого запроса/запросов найден;
- при необходимости текущая позиция.

Главное действие:

- `Добавить в benchmark` / checkbox.

Выбранные товары визуально очевидны.

Перед сохранением показывается количество выбранных конкурентов.

После изменения состава:

> Benchmark изменён. Пересчитываем аналитику…

После завершения:

> Benchmark обновлён: 8 конкурентов.

## Дедупликация кандидатов

Если один SKU найден по нескольким запросам, он показывается один раз с указанием нескольких источников обнаружения.

## Query-level benchmark

Основная benchmark-группа принадлежит собственному SKU.

При расчёте benchmark по конкретному запросу используются члены этой benchmark-группы, для которых есть валидное наблюдение по данному запросу/периоду.

UI обязан показывать фактический sample size.

`Нет наблюдения`, `не найден в отслеживаемом диапазоне` и `нет данных источника` не должны молча превращаться в одно и то же значение.

Если источник позволяет различать эти состояния, SCOZ обязан сохранять и показывать различие.

# 12. CJM — главный экран «Диагностика»

## Цель

За один экран понять основной источник отставания.

## 12.1. Верхний verdict

Первым смысловым элементом показывается итог относительно benchmark.

Пример:

> **Продажи на 38% ниже benchmark**

Под ним один главный диагноз:

> **Главный провал — недостаточная видимость.**

И короткое объяснение:

> Показы значительно ниже конкурентов, при этом конверсия находится около benchmark.

## 12.2. Основные KPI

Основной экран ограничивается компактным набором:

- продажи;
- трафик / показы;
- показ → заказ;
- карточка → корзина;
- при необходимости поиск → корзина.

Формат:

> `Мы → Benchmark → Δ → статус`

Не показывать одновременно median + P75 + индекс 100 + процентный gap + цвет.

P25/P75 уходят в детализацию.

## 12.3. Контекст оффера

Компактная строка:

> Цена выше benchmark · доставка хуже · рейтинг на уровне

Показывать только действительно полезные факторы.

## 12.4. Рекламная интенсивность

Компактный контекст:

> **Рекламная поддержка:** 690 ₽/продажу · benchmark 320 ₽ · +116%

При необходимости рядом ДРР.

Не создавать отдельный рекламный dashboard.

## 12.5. Диагнозы

Показывать максимум 2–3 причины, отсортированные по значимости.

Каждый диагноз должен быть раскрываемым и иметь доказательную базу.

Пример раскрытия:

> Почему SCOZ так считает?

После раскрытия пользователь видит конкретные показатели и benchmark, а не внутренний технический rule ID.

# 13. CJM — раздел «Поиск»

## 13.1. Первый уровень — «Поисковые возможности»

Query Opportunity является способом выбрать, куда смотреть дальше.

Для каждого запроса показывать:

- текст запроса;
- спрос;
- один ключевой показатель качества интента;
- нашу позицию / медианную позицию за период;
- benchmark позиции;
- краткий прозрачный вердикт.

Пример:

| Запрос | Спрос | CR рынка | Мы | Benchmark | Вердикт |
|---|---:|---:|---:|---:|---|
| смеситель для кухни | высокий | 11,4% | 38 | 9 | Высокий потенциал |

Не вводить Opportunity Score 0–100 в первой версии.

## 13.2. Position Stability

В детализации запроса показывать:

- Share of TOP-10;
- Share of TOP-20;
- benchmark Share of Top;
- при необходимости мини-график позиции во времени.

Это позволяет отличить устойчивость от случайной позиции одного дня.

## 13.3. Выбор запроса

После клика выбранный запрос становится активным контекстом и остаётся визуально заметным над heatmap.

Пользователь всегда должен видеть, для какого запроса сейчас анализирует кластеры.

---

# 14. CJM — кластерная heatmap

После выбора запроса пользователь видит кластеры.

Основная таблица:

| Кластер | Позиция | Релевантность | Популярность | Доставка | Цена |
|---|---:|---:|---:|---:|---:|

Не добавлять на основной уровень:

- сводную оценку;
- CPC;
- CPO;
- отзывы;
- рейтинг;
- полный price index;
- все технические признаки Ozon.

Они доступны в drill-down.

## 14.1. Системная vs локальная проблема

Над heatmap SCOZ может сформировать короткое резюме:

> Популярность ниже benchmark во всех основных кластерах. В Москве дополнительно проигрываем по доставке.

Не более 2–3 предложений.

## 14.2. «Все кластеры»

Если используется агрегированный режим, UI должен пояснять метод:

- `Взвешено по спросу`;
- либо `Невзвешенное агрегирование`, если надёжных весов нет.

Не скрывать отсутствие весов.

---

# 15. CJM — режим «Разгон»

## Цель

Ответить не на вопрос «CR ниже конкурентов?», а:

> Нормальна ли CR для текущего места и есть ли смысл покупать более высокую позицию?

## 15.1. Readiness gate

Перед показом модели SCOZ проверяет достаточность данных.

Если данных недостаточно, пользователь видит:

> **Пока недостаточно истории для оценки разгона.**

И конкретную причину, например:

> Есть 5 дневных наблюдений позиции; для текущего правила требуется больше истории.

Порог берётся из конфигурации и не должен быть выдуман UI.

Не показывать пустые графики или фиктивный прогноз.

## 15.2. Вердикт

Первый блок:

- `Кандидат на разгон`;
- `Сначала улучшить карточку/оффер`;
- `Дополнительный разгон не требуется`;
- `Проблема карточки/оффера`;
- `Недостаточно данных`.

Под ним короткое объяснение.

## 15.3. Position → Conversion

График должен различать:

- рыночные наблюдения;
- benchmark-кривую;
- собственные исторические наблюдения;
- текущую точку SKU.

Легенда обязательна.

Нельзя визуально создавать ощущение причинности, если модель основана на корреляционных данных.

## 15.4. Сценарии

Показывать:

- сейчас;
- TOP-20;
- TOP-10;
- TOP-3.

Для каждого:

- диапазон позиции;
- ожидаемую CR;
- оценочный диапазон ставки;
- confidence.

Не выводить псевдоточные ставки.

## 15.5. Органическая опора

Если накоплена достаточная история, показывать динамику оценки ставки, необходимой для удержания TOP-N.

Главная интерпретация:

> требуемая ставка снижается → товар показывает признаки закрепления.

Это наблюдаемый аналитический сигнал, а не утверждение внутренней формулы Ozon.

---

# 16. Data Readiness

SCOZ должен явно показывать, какая аналитика сейчас доступна для SKU.

Пример компактного readiness-состояния:

- `Товарные данные — свежие`;
- `Benchmark — 8 конкурентов`;
- `Поисковая видимость — есть`;
- `История позиций — 21 день`;
- `Разгон — данных недостаточно`.

Readiness нужен не для красоты, а чтобы пользователь понимал, почему один экран работает, а другой ещё нет.

Не создавать отдельный сложный health dashboard, если то же состояние можно показать компактно в Product Workspace и разделе «Данные».

---

# 17. Свежесть данных

На экранах, где свежесть влияет на решение, показывать дату/период данных.

Не ограничиваться техническим `imported_at`.

Пользователю важнее:

> Данные Ozon за 10–12 августа · импортированы сегодня 14:32

Если данные старые относительно настроенного порога, UI обозначает `Данные устарели`.

Устаревшие данные не должны автоматически блокировать просмотр, если аналитика всё ещё математически воспроизводима.

---

# 18. Loading states

## 18.1. Skeleton vs spinner

- skeleton — когда известна структура экрана и загружаются данные;
- spinner — для локального действия небольшого размера;
- progress/stage — для импорта, синхронизации и других длительных операций.

Не использовать full-screen spinner для локального пересчёта одного блока, если остальная страница остаётся валидной.

## 18.2. Сохранять стабильный layout

При обновлении данных основные блоки не должны хаотично прыгать.

Если старый результат остаётся видимым во время refresh, он помечается:

> Обновляем… показаны предыдущие данные.

---

# 19. Empty states

Каждый пустой экран обязан отвечать на два вопроса:

1. Почему здесь ничего нет?
2. Что нужно, чтобы данные появились?

Плохо:

> Нет данных.

Хорошо:

> Нет данных по поисковой видимости для этого SKU. Загрузите отчёт «Что влияет на место» или синхронизируйте источник Ozon.

Если действие уже возможно, рядом размещается соответствующая кнопка.

---

# 20. Error states

Ошибка должна быть actionable.

Минимальная структура:

- человеческое описание;
- что осталось сохранено/не повреждено;
- можно ли повторить;
- понятное действие `Повторить` / `Выбрать другой файл` / `Открыть настройки`;
- технический код/детали — по раскрытию.

Для API-ошибки различать как минимум:

- нет подключения;
- неверные credentials;
- rate limit;
- временная ошибка источника;
- несовместимый ответ источника.

Не показывать пользователю raw stack trace как основной текст.

---

# 21. Success и notifications

Toast используется только для коротких подтверждений, которые не нужно перечитывать.

Критически важный результат должен оставаться в контексте страницы.

Например, после сохранения benchmark-группы:

- допустим toast `Benchmark сохранён`;
- но количество конкурентов и новое состояние benchmark остаются видимыми на экране.

Не использовать поток зелёных toast на каждое автоматическое действие.

---

# 22. Детализация benchmark

По клику на benchmark-показатель открывается drawer/modal/detail view с:

- нашим значением;
- медианой;
- P25/P75;
- sample size;
- списком включённых конкурентов;
- их значениями;
- периодом;
- источником/свежестью;
- объяснением статуса.

Пользователь должен иметь возможность проверить вывод, но не обязан видеть эту детализацию постоянно.

---

# 23. Форматирование чисел

Использовать понятные локальные форматы:

- `31 200` вместо `31200`;
- `52,6 ₽`;
- `11,4%`;
- разумное количество знаков после запятой;
- `+12%` / `−38%`;
- процентные пункты явно обозначать `п.п.`, когда это именно разница процентных показателей.

Не показывать больше точности, чем даёт источник или модель.

---

# 24. Desktop-first и Windows usability

SCOZ — desktop-first browser UI.

Основной целевой сценарий — Windows desktop/laptop.

Требования:

- главные экраны должны оставаться читаемыми на типичных рабочих разрешениях без горизонтальной прокрутки;
- учитывать Windows scaling 125–150%;
- raw/detail tables могут иметь горизонтальный scroll, основные аналитические screens — нет;
- кликабельные области и controls должны быть достаточно крупными для обычной мыши;
- hover не должен быть единственным способом получить критически важную информацию.

Mobile-first адаптация не является целью первой версии.

---

# 25. Клавиатура и доступность

Минимальные требования:

- логичный tab order;
- visible focus;
- buttons имеют текст/accessible name;
- цветовые статусы дублируются текстом/символом;
- таблицы имеют понятные headers;
- modals/drawers корректно удерживают и возвращают focus.

---

# 26. UX секретов и подключений

В `Настройки → Источники` пользователь видит:

- источник;
- статус подключения;
- дату последней успешной синхронизации;
- кнопку `Проверить подключение`;
- masked credentials.

После проверки:

> Ozon Seller API: подключение успешно

или понятная ошибка.

Секрет никогда не отображается обратно полностью и не передаётся frontend после сохранения.

---

# 27. Приоритеты и отказ от перегруза

На основном уровне SCOZ сознательно не показывает:

- универсальный score карточки 0–100;
- Opportunity Score 0–100;
- десятки KPI одновременно;
- все поля Ozon Explainer;
- отдельный рекламный BI;
- «цену продавца» / СПП-подобные вычисления;
- оценочные рекламные/органические продажи конкурентов.

Если новая функция добавляет данные, но не помогает принять решение по основным JTBD, она должна оставаться в детализации или не включаться в первую версию.

# 29. UX telemetry без центрального сервера

В первой версии не требуется внешняя продуктовая telemetry.

Для диагностики приложения допустим локальный технический журнал действий/ошибок без секретов и коммерческого содержимого сверх необходимого.

Система не должна зависеть от внешнего analytics SDK для нормальной работы.

---

# 30. Требования к frontend architecture из UX

Frontend должен иметь явные состояния view models.

Не рекомендуется строить UX на предположении, что `data == null` означает одновременно loading, empty и error.

Для сложных экранов API/view model должен позволять различать:

- loading / refresh;
- ready;
- stale;
- empty;
- insufficient data;
- partial data;
- source error.

Аналитические reason codes формируются backend/application layer, а frontend отвечает за понятное представление.

---

# 31. Acceptance criteria UI/UX foundation

UI/UX фундамент считается корректным, когда:

1. Пользователь всегда видит активный SKU и период на аналитических экранах.
2. Любая долгая операция показывает текущую стадию или понятное состояние.
3. После клика невозможно остаться без признака, что действие принято.
4. Loading, empty, error, partial success и insufficient data визуально различаются.
5. Главная диагностика не содержит более необходимого набора KPI и максимум 2–3 ключевых выводов.
6. Benchmark-группа редактируется визуально через фото кандидатов.
7. Изменение benchmark-группы явно запускает и завершает пересчёт.
8. Query Opportunity является частью поискового workflow, а не отдельным BI-разделом.
9. Активный запрос видим при просмотре кластерной heatmap.
10. Режим «Разгон» не строит прогноз при недостатке данных и объясняет причину.
11. Свежесть и период данных видны там, где они влияют на решение.
12. Пользователь может раскрыть benchmark и проверить состав выборки.
13. Цвет не является единственным способом понять статус.
14. Основные screens не требуют горизонтальной прокрутки на целевом desktop layout.
15. API credentials не отображаются frontend в открытом виде.

---

# 32. UX-инварианты для code review

Будущий PR требует корректировки, если он приводит хотя бы к одному из следующих состояний без отдельного согласованного изменения design:

- кнопка запускает долгую операцию без feedback;
- spinner длительно показывается без пояснения стадии;
- пустой экран не объясняет причину и следующий шаг;
- stale данные выглядят как свежие;
- ошибка API скрывается или показывается только техническим trace;
- frontend самостоятельно рассчитывает benchmark/диагноз;
- выбранный SKU/query/period теряется из контекста;
- на главный экран добавляется новый показатель без понятного JTBD;
- Query Opportunity превращается в отдельный dashboard;
- рекламная аналитика вытесняет основной диагноз;
- модельный прогноз показывается как факт;
- insufficient data заменяется псевдоточным прогнозом;
- benchmark sample size скрывается при неполной выборке;
- отсутствующая позиция конкурента молча интерпретируется как обычное числовое значение.

---

# 33. Связь с PR Development Plan

PR-план должен учитывать UI/UX не как финальную «полировку», а как функциональное требование каждого вертикального PR.

Например:

- PR импорта обязан включать loading/progress/result/error states;
- PR benchmark-группы обязан включать feedback пересчёта;
- PR диагностики обязан включать empty/insufficient/partial-data states;
- PR Query Opportunity обязан сохранять активный query context;
- PR «Разгон» обязан включать readiness gate до графиков и прогнозов;
- PR source adapters обязан показывать connection/sync state.

UI/UX acceptance criteria должны входить в ТЗ соответствующего PR и проверяться вместе с функциональной логикой.
