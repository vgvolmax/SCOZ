# SCOZ — UI/UX Design

**Дата:** 2026-08-13  
**Статус:** канонический UI/UX design

## 1. UX North Star

> **Пользователь всегда понимает: где он находится, что сейчас анализируется, что система делает, какой результат получен и что мешает получить результат.**

SCOZ не должен ощущаться как BI-конструктор.

Приоритет представления:

> **Ответ → причина → подтверждающие показатели → исходные данные.**

Сложность скрывается progressive disclosure, а не дополнительными role-based интерфейсами.

## 2. Базовые принципы

- Никаких «тихих» действий: click/import/sync/recalculation всегда дают видимый feedback.
- Активный SKU, period, benchmark revision и выбранный query остаются видимыми в контексте.
- Loading, refresh, empty, partial success, error, stale и insufficient-data различаются.
- Цвет не является единственным носителем смысла.
- Fact / calculated metric / model estimate не должны визуально смешиваться.
- Не показывать псевдоточность, особенно в «Разгоне».
- Первый экран не должен требовать знания методологии.

## 3. Основные JTBD

### JTBD-1 — диагностировать SKU

Когда продажи хуже ожиданий, пользователь хочет сразу понять главный источник отставания относительно прямых competitors.

### JTBD-2 — выбрать ценные queries

Когда проблема в поисковой видимости, пользователь хочет видеть не длинный список запросов, а поисковые возможности, где есть demand, хороший intent и реальный visibility gap.

### JTBD-3 — понять географию проблемы

По выбранному query пользователь хочет различить системный провал и проблему отдельного кластера/доставки.

### JTBD-4 — отличить плохую карточку от плохого места

Пользователь хочет понять, нормальна ли CR для текущей позиции.

### JTBD-5 — решить, нужен ли «Разгон»

При нормальной position-normalized CR пользователь хочет оценить, имеет ли смысл покупать более высокую позицию и какие диапазоны scenarios выглядят реалистично.

### JTBD-6 — увидеть закрепление

После разгона пользователь хочет видеть, снижается ли рекламная поддержка, требуемая для удержания сопоставимой позиции.

### JTBD-7 — сформировать честный benchmark

Пользователь хочет по фото и основным признакам выбрать только реально сопоставимые товары.

### JTBD-8 — доверять данным

При импорте/sync пользователь хочет видеть period, freshness, что принято/пропущено и почему аналитика доступна или недоступна.

## 4. Информационная архитектура

Глобальная навигация:

1. **Товары** — основной рабочий раздел.
2. **Данные** — imports/sync/history.
3. **Настройки** — sources и API credentials.

Не создавать отдельные глобальные разделы `Benchmark`, `Реклама`, `Query Opportunity`, `Кластеры`.

Внутри Product Workspace:

- **Диагностика**;
- **Поиск**;
- **Разгон**;
- **Конкуренты**.

## 5. Product Workspace header

На аналитических экранах постоянно видны:

- фото/title/SKU own product;
- active period;
- freshness;
- benchmark composition/status;
- data readiness;
- active query, когда открыт Search flow.

Header не перегружать KPI.

## 6. CJM — первый запуск

Пользователь запускает `start.bat`.

Launcher показывает человеческие стадии, например:

- `Подготавливаем приложение`;
- `Проверяем компоненты`;
- `Обновляем базу данных`, если требуется;
- `Запускаем SCOZ`.

Browser открывается только после успешного health check.

Если запуск не удался, пользователь видит понятную причину/следующий шаг и путь к логу.

Если данных ещё нет, вместо пустого dashboard показывается readiness-screen:

> Для анализа загрузите данные Ozon и выберите собственный товар.

Основное действие — `Загрузить отчёт`; если API adapter уже реализован, рядом доступна настройка source.

Длинный onboarding wizard не нужен.

## 7. CJM — импорт данных

Flow:

1. пользователь выбирает файл;
2. UI сразу показывает выбранный файл;
3. определяется тип отчёта;
4. показывается текущая стадия;
5. после импорта отображается результат;
6. затронутая аналитика обновляется.

Пример стадий:

- `Проверяем файл`;
- `Читаем данные`;
- `Нормализуем`;
- `Сохраняем`;
- `Обновляем аналитику`.

Процент показывается только если он честно вычисляется.

Результат импорта показывает:

- report type;
- period;
- imported rows;
- skipped rows;
- warnings/errors;
- duplicate/revision status;
- что стало доступно после импорта.

`PARTIAL_SUCCESS` визуально отличается от полного успеха.

## 8. Feedback contract без переусложнения

UI не требует persistent operations platform.

Короткие действия используют локальное loading state. Длительные действия при необходимости используют lightweight polling.

Минимально различать:

`VALIDATING → RUNNING → SUCCESS / PARTIAL_SUCCESS / FAILED`.

Если старый результат остаётся на экране во время refresh, он помечается:

> Обновляем… показаны предыдущие данные.

## 9. CJM — benchmark competitors

Кандидат показывается карточкой/строкой с:

- главным фото;
- title;
- SKU;
- brand/price при наличии;
- controls include/exclude.

Всегда видно количество выбранных competitors.

Сохранение создаёт новую benchmark revision и показывает завершение пересчёта.

Отсутствие фото не означает отсутствие товара.

Benchmark details по клику показывают own value, median, P25/P75 при достаточной sample, sample size, competitor values, period/freshness и confidence.

## 10. CJM — Диагностика

Первый уровень:

- продажи относительно benchmark;
- traffic;
- impression→order conversion;
- card/search→cart по доступности;
- compact offer context;
- compact advertising-intensity context;
- максимум 2–3 ключевых вывода.

Пользователь не должен сам собирать диагноз из десятков таблиц.

По `Почему SCOZ так считает?` раскрываются конкретные факторы/benchmark, а не internal rule ID.

Если OOS или маленькая sample искажают вывод, это видно рядом с диагнозом.

## 11. CJM — Поиск

Первый блок — **Поисковые возможности**.

Для каждого query показывать:

| Query | Demand | Market quality | Мы | Benchmark | Verdict |
|---|---:|---:|---:|---:|---|

Не создавать Opportunity Score 0–100.

После клика query становится активным контекстом и ниже открывается cluster heatmap:

| Кластер | Позиция | Релевантность | Популярность | Доставка | Цена |
|---|---:|---:|---:|---:|---:|

CPC/CPO/reviews/rating/прочие Explainer fields — drill-down.

Для `Все кластеры` UI явно пишет `Взвешено по спросу` или `Невзвешенное агрегирование`.

Position Stability в details показывает Share of TOP-10/TOP-20 с denominator и при необходимости mini-history.

## 12. CJM — Разгон

Перед моделями работает readiness gate.

Если данных недостаточно:

> **Пока недостаточно истории для оценки разгона.**

И обязательно объясняется, чего не хватает.

Основной verdict:

- `Кандидат на разгон`;
- `Сначала улучшить карточку/оффер`;
- `Дополнительный разгон не требуется`;
- `Проблема карточки/оффера`;
- `Недостаточно данных`.

Основные области экрана:

1. verdict + короткое объяснение;
2. `position → conversion` только при честной evidence base;
3. scenarios `Сейчас / TOP-20 / TOP-10 / TOP-3` с ranges/confidence;
4. organic-support trend при достаточной history.

UI не создаёт впечатление доказанной causality и не показывает псевдоточные ставки.

Granularity модели в детализации должна быть понятна; cluster-level scenarios не показываются без cluster-level evidence.

## 13. Data Readiness и freshness

Для SKU компактно показывать, какие блоки данных доступны, например:

- `Товарные данные — свежие`;
- `Benchmark — 8 competitors`;
- `Поисковая видимость — есть`;
- `История позиций — 21 день`;
- `Разгон — данных недостаточно`.

На аналитике показывается business period и imported time, например:

> Данные Ozon за 10–12 августа · импортированы сегодня 14:32.

Stale data можно просматривать, но они не выглядят свежими.

## 14. Empty/error states

Каждый empty state отвечает:

1. почему данных нет;
2. что нужно сделать.

Ошибка должна быть actionable: человеческое описание, что осталось сохранено, можно ли повторить, понятное действие и техническая detail только по раскрытию.

Для source API различать как минимум connection/auth/rate-limit/temporary/schema errors, если adapter способен это определить.

Raw stack trace не является пользовательским сообщением.

## 15. API credentials UX — выбранный portable keystore

В `Настройки → Источники` пользователь видит источник, поля credentials, `Проверить подключение` и текущий статус.

Пользователь может работать двумя способами:

### Ввести ключи вручную

Ключи активны только в текущей browser tab.

### Сохранить зашифрованный файл

UI предлагает пароль + повтор пароля и сохраняет `scoz_credentials.enc.json` в утверждённом encrypted-keystore формате.

### Открыть зашифрованный файл

Пользователь выбирает/перетаскивает `.enc.json`, вводит пароль и нажимает `Расшифровать`.

При успехе sources заполняются/становятся active только в памяти текущей вкладки.

### Заблокировать ключи

Кнопка `Заблокировать ключи` очищает credentials из памяти.

После reload/закрытия вкладки ключи нужно ввести или разблокировать снова — это нормальное поведение внутреннего portable-инструмента.

Plaintext credentials не сохраняются в SQLite/конфиг и не отображаются обратно после потери текущего in-memory состояния.

## 16. Desktop-first

Target — Windows desktop/laptop.

Основные analytics screens не требуют горизонтальной прокрутки на типичных рабочих разрешениях и учитывают Windows scaling 125–150%.

Raw/detail tables могут иметь horizontal scroll.

Mobile-first не является целью v1.

Минимальная accessibility: visible focus, логичный tab order, понятные headers, цвет дублируется текстом/символом, hover не является единственным носителем critical info.

## 17. Числа и ложная точность

Использовать локальные читаемые formats: `31 200`, `52,6 ₽`, `11,4%`, `+12%`, `−38%`, `п.п.` для percentage points.

Не показывать больше precision, чем даёт source/model.

Fact, calculation и estimate визуально/в детализации различимы.

## 18. Что сознательно не показываем на основном уровне

- universal card score 0–100;
- Opportunity Score 0–100;
- десятки KPI;
- все Explainer fields;
- отдельный advertising BI;
- seller-price/SPP-like calculations;
- estimated competitor ad/organic sales;
- technical provenance без запроса пользователя.

## 19. UX invariants для code review

PR требует корректировки, если пользователь нажимает действие без feedback; spinner висит без смысла на длительной операции; empty state не объясняет следующий шаг; stale выглядит как fresh; active SKU/query/period теряется; model estimate выглядит как факт; small benchmark sample выглядит уверенно; Query Opportunity превращается в отдельный dashboard; credentials сохраняются plaintext; API-key flow становится сложнее утверждённого portable keystore без нового design change.

## 20. Acceptance criteria UI/UX foundation

UI/UX foundation считается соблюдённым, когда пользователь всегда видит активный контекст и freshness, импорт/sync/recalculation дают feedback, empty/error/partial/insufficient states понятны, benchmark выбирается визуально и пересчитывается явно, Query Opportunity ведёт в существующую heatmap, Ramp-up имеет readiness gate, credentials можно удобно сохранить/открыть через encrypted portable keystore, а основной интерфейс остаётся простым и decision-oriented.
