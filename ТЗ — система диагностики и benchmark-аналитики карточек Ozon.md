# 1. Назначение системы

Разработать аналитическое приложение для оценки собственных карточек товаров на Ozon относительно **выбранной группы реальных конкурентов**.

Система должна отвечать на два разных бизнес-вопроса.

### Режим 1. Диагностика

> Где наша карточка проигрывает выбранным конкурентам и чем это объясняется?

Система должна последовательно определить:

**результат → трафик → конверсию → поисковую видимость → факторы ранжирования → конкретные запросы и кластеры, где возникает провал.**

### Режим 2. Разгон

> Низкая конверсия товара действительно связана с качеством карточки или она является следствием низкой позиции в выдаче?

Дополнительно:

> Есть ли экономический и поведенческий смысл временно повысить рекламную ставку, вывести товар выше, получить лучшую конверсию/заказы и после усиления органической позиции постепенно снизить ставку?

Оба режима используют одну базу данных, но решают разные аналитические задачи и должны быть разделены в интерфейсе.

---

# 2. Основной продуктовый принцип

Система не должна превращаться в BI-панель с большим количеством показателей.

Основной пользовательский сценарий:

1. Пользователь выбирает свой товар.
2. Видит общий диагноз относительно выбранных конкурентов.
3. Видит главный источник отставания.
4. При необходимости проваливается в поисковые запросы и кластеры.
5. Видит конкретный фактор, создающий разрыв.
6. Отдельно может открыть режим «Разгон» и проверить влияние позиции на конверсию.

Главный экран должен быть понятен без изучения методологии расчёта.

Все дополнительные показатели, исходные значения конкурентов, квартили, реклама и техническая информация должны находиться на втором уровне детализации.

---

# 3. Источники данных

Архитектура должна быть независимой от конкретного способа получения данных.

Для каждого источника необходимо предусмотреть отдельный адаптер.

На первом этапе допускается импорт XLSX. В дальнейшем XLSX должен заменяться API без изменения аналитического ядра.

## 3.1. Ozon — «Товары на Ozon»

Основной источник конкурентных товарных показателей.

Используются доступные в отчёте показатели, включая:

- продажи в штуках;
- выручку;
- показы;
- просмотры поиска/каталога;
- просмотры карточки;
- конверсию;
- добавление в корзину из поиска;
- добавление в корзину из карточки;
- цену;
- остатки;
- рекламные и прочие вспомогательные показатели, если они присутствуют.

Не все загружаемые показатели обязательно отображаются пользователю.

Система должна хранить исходные данные максимально полно, чтобы впоследствии можно было расширять аналитику без повторного импорта.

---

# 3.2. Ozon — «Видимость в поиске / Что влияет на место»

Источник данных уровня:

**дата × поисковый запрос × кластер × SKU.**

Храним как минимум:

- поисковый запрос;
- кластер;
- SKU;
- позицию;
- сводную оценку Ozon;
- соответствие запросу;
- популярность;
- условия продвижения;
- CPC;
- оплату за заказ, если присутствует;
- срок доставки;
- цену;
- индекс цены;
- рейтинг;
- количество отзывов;
- прочие присутствующие в отчёте факторы.

Сводная оценка и часть дополнительных факторов сохраняются в базе, даже если не выводятся на основном экране.

---

# 3.3. Ozon — аналитика собственного товара / поисковые запросы

Использовать для собственного товара доступную историю:

- поисковых запросов;
- видимости;
- позиции;
- показов;
- переходов;
- конверсий;
- заказов;
- других доступных показателей.

Гранулярность данных должна сохраняться максимально близко к исходной.

---

# 3.4. Ozon Performance API

Используется только для собственных товаров и рекламных кампаний.

Не является основным источником конкурентных benchmark.

Нужен прежде всего режиму «Разгон» для построения истории:

**ставка → рекламное воздействие → позиция → конверсия → заказы → изменение поисковых факторов → последующее изменение требуемой ставки.**

---

# 3.5. MPStats

MPStats не используется как источник основных числовых benchmark.

Основная задача MPStats:

> получение главных фотографий товаров-кандидатов для визуального отбора действительно сопоставимых конкурентов.

Архитектура должна позволять впоследствии заменить источник изображений без изменения модели конкурентов.

---

# 4. Модель конкурентов

Benchmark нельзя считать по всей выдаче Ozon.

Для каждого собственного SKU должна существовать явно сохранённая **benchmark-группа**.

## Процесс формирования

Система получает товары-кандидаты из поисковой выдачи по релевантным запросам.

Для кандидатов загружаются:

- название;
- SKU;
- бренд;
- цена;
- главное фото;
- при наличии — основные товарные характеристики.

Пользователь выбирает товары, которые действительно являются прямыми конкурентами по назначению, типу товара и покупательскому выбору.

После подтверждения список сохраняется.

Benchmark рассчитывается **только по выбранным конкурентам**.

Пользователь должен иметь возможность:

- добавить конкурента;
- удалить конкурента;
- заменить конкурента;
- просмотреть фотографию;
- посмотреть исходные показатели товара.

Изменение benchmark-группы должно автоматически приводить к пересчёту аналитики.

---

# 5. Общая математическая модель benchmark

Основной benchmark по показателю:

> **медиана выбранных конкурентов.**

Среднее арифметическое не должно быть базовым benchmark, так как отдельный крупный конкурент может сильно искажать результат.

Дополнительно система может рассчитывать:

- P25;
- P75;
- минимум;
- максимум;
- размер выборки.

На основном экране они не выводятся по умолчанию.

Основное представление:

**Наш показатель | Benchmark | отклонение**

Отклонение:

`(наш показатель / benchmark - 1) × 100%`

Для показателей, где меньшее значение является лучшим, направление оценки должно инвертироваться.

---

# 6. Статусы benchmark

Статус должен определяться не универсальным порогом, а положением собственного товара относительно распределения выбранных конкурентов.

Базовая схема:

- 🟢 на уровне или выше медианы;
- 🟡 между P25 и медианой;
- 🔴 ниже P25.

Для показателей, где меньшее значение лучше, логика инвертируется.

Цвет является средством навигации, но рядом всегда должно отображаться фактическое значение.

Не создавать единую синтетическую «оценку карточки 0–100».

---

# 7. Режим «Диагностика»

## 7.1. Главный экран товара

Экран должен сразу отвечать:

> Почему мы продаём хуже или лучше выбранных конкурентов?

Наверху показывается итоговый результат:

**Продажи, шт. → отклонение от benchmark**

Далее три основных диагностических блока.

### Трафик

Основной показатель:

**показы**

### Конверсия

Основной показатель:

**показ → заказ**

Дополнительные:

- поиск/каталог → корзина;
- карточка → корзина.

### Оффер

Не должен занимать большой самостоятельный блок.

Кратко показываются значимые контекстные показатели:

- цена относительно benchmark;
- доставка;
- рейтинг/отзывы при наличии существенного разрыва.

Пример логики экрана:

| Показатель | Мы | Benchmark | Δ |
|---|---:|---:|---:|
| Продажи | 42 | 110 | 🔴 −62% |
| Показы | 31 000 | 82 000 | 🔴 −62% |
| Показ → заказ | 0,14% | 0,16% | 🟡 −13% |
| Карточка → корзина | 9,1% | 8,8% | 🟢 +3% |

Контекст:

**Цена +5% · доставка хуже benchmark · рейтинг на уровне**

Из такого набора система должна уметь сформировать вывод:

> Продажи ниже benchmark преимущественно из-за недостаточного трафика. Конверсия близка к конкурентам, а конверсия карточки находится на уровне benchmark.

---

# 8. Автоматическая диагностика

Система должна не только показывать цифры, но и определять структуру проблемы.

Минимальные классы диагнозов:

### Недостаток трафика

Продажи ниже benchmark преимущественно из-за значительно меньшего количества показов при нормальной конверсии.

### Слабая конверсия

Трафик соответствует benchmark, но переходы/заказы существенно хуже.

### Проблема внутри карточки

Пользователь переходит в карточку, но плохо добавляет товар в корзину.

### Проблема выдачи

Карточка нормально продаёт после перехода, но добавление в корзину непосредственно из поиска ниже benchmark.

### Проблема оффера

Сильное отклонение цены, доставки или других коммерческих условий при сопоставимой видимости.

### Комбинированный провал

Одновременно значительно хуже и трафик, и конверсия.

На основном экране показываются максимум **2–3 наиболее существенные причины**.

Не выводить пользователю длинный автоматически сформированный аналитический текст.

---

# 9. Анализ поисковой видимости

Поисковая аналитика строится в гранулярности:

> **SKU × запрос × кластер**

Пользователь сначала выбирает поисковый запрос.

После этого отображается heatmap по кластерам.

Основная таблица:

| Кластер | Позиция | Релевантность | Популярность | Доставка | Цена |
|---|---:|---:|---:|---:|---:|

Цвет каждого фактора определяется относительно benchmark-группы.

Основной смысл:

> показать не абсолютные значения, а географию и структуру отставания.

Например:

- популярность ниже benchmark во всех кластерах → системная проблема;
- доставка проигрывает только в Москве → локальная проблема;
- релевантность нормальна → SEO не является главным ограничением.

---

# 10. Что не показывается в основной heatmap

Не перегружать основной экран следующими показателями:

- сводная оценка;
- CPC;
- оплата за заказ;
- рейтинг;
- отзывы;
- подробный индекс цены;
- дополнительные технические факторы.

Они сохраняются в данных и доступны при раскрытии строки кластера или товара.

---

# 11. Общий benchmark по кластерам

Кроме отдельных кластеров нужен режим:

**Все кластеры**

Он не должен рассчитываться простым средним.

Если доступен объём спроса/трафика по кластеру, необходимо использовать взвешивание по потенциальному спросу.

Условно:

`общий показатель = Σ(показатель кластера × вес кластера)`

Если надёжного веса нет, система должна явно обозначать расчёт как невзвешенный и не создавать ложную точность.

---

# 12. Реклама в режиме диагностики

Реклама является контекстом, но не должна занимать отдельный крупный блок.

При наличии данных показывать компактно:

> Продвижение: да · CPC 52,6 ₽ · benchmark 47,8 ₽

Если рекламные показатели существенно помогают объяснить проблему, система включает их в автоматический диагноз.

Пример:

> Ставка уже выше benchmark, однако позиция существенно хуже. Простое повышение ставки без устранения базового разрыва может быть неэффективно.

---

# 13. Отдельный режим «Разгон»

Режим не смешивается с обычной диагностикой.

Главный вопрос:

> Является ли низкая абсолютная конверсия товара следствием плохой карточки или нормальным следствием его текущего места в выдаче?

---

# 14. Позиционно-нормализованная конверсия

Нельзя сравнивать нашу CR с общей CR конкурентов без учёта места.

Система должна строить зависимость:

**позиция → типичная конверсия**

на основе накопленных наблюдений.

Базовые диапазоны позиции могут быть:

- 1–3;
- 4–10;
- 11–20;
- 21–50;
- 51–100;
- 100+.

Диапазоны должны быть конфигурируемыми.

Для каждого диапазона рассчитывается типичная CR.

После этого система сравнивает нашу фактическую CR не со всей benchmark-группой, а с товарами/наблюдениями на сопоставимых местах.

Пример:

> Наша позиция: 74  
> Наша CR: 0,31%  
> Типичная CR позиции 51–100: 0,30%

Диагноз:

> 🟢 Конверсия соответствует текущему уровню позиции. Низкая абсолютная CR сама по себе не свидетельствует о проблеме карточки.

Другой пример:

> Наша CR: 0,15%  
> Benchmark позиции: 0,30%

Диагноз:

> 🔴 Низкая конверсия не объясняется позицией. Перед увеличением рекламной ставки необходимо проверить карточку и оффер.

---

# 15. Историческая модель

Главная аналитическая таблица режима «Разгон»:

**дата × SKU × запрос × кластер × позиция × ставка × конверсия × заказы × факторы поисковой видимости**

Данные должны накапливаться во времени.

Особенно важны наблюдения одного и того же SKU при изменении позиции.

Система должна различать:

### Cross-sectional данные

Разные товары в один момент времени.

Используются как приблизительный рыночный benchmark.

### Longitudinal данные

Один товар в разные моменты времени.

Имеют больший вес при оценке влияния позиции на конверсию конкретного SKU.

По мере накопления истории модель должна переходить от общего рыночного benchmark к персональной кривой SKU.

---

# 16. Ограничение интерпретации данных

Нельзя автоматически считать агрегированную конверсию товара из отчёта «Товары на Ozon» конверсией конкретной позиции по конкретному запросу.

Например, запрещена логика:

> конкурент находится на позиции №1 по запросу X → его общая CR 0,6% → значит CR первой позиции равна 0,6%.

Это разные уровни агрегации.

Система должна явно учитывать это ограничение.

При недостаточной детализации вывод обозначается как **оценочный**, а не фактический.

---

# 17. Сценарный расчёт разгона

Система должна уметь показывать ориентировочные сценарии:

| Сценарий | Ожидаемая позиция | Ожидаемая CR | Оценочная ставка |
|---|---:|---:|---:|
| Сейчас | 74 | 0,31% | 50 ₽ |
| TOP-20 | 11–20 | ~0,50% | диапазон |
| TOP-10 | 5–10 | ~0,60% | диапазон |
| TOP-3 | 1–3 | ~0,68% | диапазон |

Расчёт не должен создавать ложную точность.

Не выводить:

> «183,47 ₽ гарантирует позицию №8».

Выводить диапазон:

> «Для попадания в TOP-10 исторические данные указывают на рабочую область примерно 180–220 ₽».

---

# 18. Связь ставки и позиции

Система должна эмпирически строить зависимость:

**ставка → позиция**

для собственного SKU, запроса и кластера.

По мере накопления данных учитывать также изменение состояния товара во времени.

Если при одинаковой позиции постепенно требуется меньшая ставка, это является важным сигналом укрепления товара.

---

# 19. Органическая опора

Не использовать термин «внутренняя база Ozon» как установленный факт, так как внутренняя формула ранжирования неизвестна.

Рабочий аналитический термин:

**органическая опора товара**

Она наблюдается через способность товара удерживать определённую позицию при меньшем рекламном воздействии.

Один из главных практических показателей:

> **оценочная ставка, необходимая сейчас для удержания TOP-N.**

Например:

| Дата | Ставка для TOP-10 |
|---|---:|
| 13.08 | ~210 ₽ |
| 20.08 | ~170 ₽ |
| 27.08 | ~130 ₽ |
| 03.09 | ~95 ₽ |

Диагноз:

> Товар закрепляется: для удержания сопоставимой позиции требуется всё меньшая рекламная ставка.

---

# 20. Основной вердикт режима «Разгон»

Экран должен автоматически относить товар к одному из четырёх сценариев:

| Позиция | CR относительно позиции | Вывод |
|---|---|---|
| Низкая | Нормальная | 🟢 Кандидат на разгон |
| Низкая | Плохая | 🔴 Сначала улучшить карточку/оффер |
| Высокая | Нормальная | 🟢 Дополнительный разгон не требуется |
| Высокая | Плохая | 🔴 Проблема карточки/оффера |

Это центральный пользовательский результат режима.

---

# 21. Интерфейс режима «Разгон»

Экран должен состоять максимум из четырёх смысловых областей.

### 1. Вердикт

Например:

> 🟢 **Кандидат на разгон**  
> Текущая CR соответствует benchmark для позиции 51–100. Основное ограничение — место в выдаче.

### 2. График

**X — позиция**  
**Y — конверсия**

На графике:

- рыночные наблюдения;
- benchmark-кривая;
- собственные исторические наблюдения;
- текущая точка товара.

### 3. Сценарии

Краткая таблица:

**Сейчас / TOP-20 / TOP-10 / TOP-3**

с ожидаемой CR и оценочным диапазоном ставки.

### 4. Закрепление

Динамика:

**ставка, необходимая для удержания выбранного TOP-N**

Если данных недостаточно, блок не строится.

---

# 22. Работа с недостаточными данными

Система не должна выдавать сильный вывод при маленькой выборке.

Для каждого аналитического результата необходимо хранить:

- количество наблюдений;
- количество конкурентов;
- период;
- наличие собственной истории;
- степень достаточности данных.

Минимальный пользовательский статус:

- высокая уверенность;
- средняя;
- данных недостаточно.

Пороговые значения должны задаваться конфигурацией, а не быть зашиты в UI.

---

# 23. Хранение истории

Импорт нового отчёта не должен перезаписывать предыдущий snapshot.

Каждая загрузка сохраняется как историческое наблюдение.

Нужно уметь восстановить состояние:

- товара;
- конкурента;
- поискового запроса;
- кластера;
- позиции;
- benchmark;
- рекламных параметров

на конкретную дату.

Это обязательное требование для режима «Разгон».

---

# 24. Идентификация сущностей

Необходимо иметь стабильные внутренние сущности:

### Product
Товар Ozon.

### OwnProduct
Собственный товар.

### CompetitorProduct
Потенциальный/выбранный конкурент.

### BenchmarkSet
Сохранённая группа конкурентов для собственного SKU.

### SearchQuery
Поисковый запрос.

### Cluster
Кластер Ozon.

### ProductSnapshot
Показатели товара на дату.

### SearchVisibilitySnapshot
Данные:

**SKU × query × cluster × date**

### AdvertisingSnapshot
Ставка и рекламные показатели собственного товара.

### BenchmarkSnapshot
Рассчитанное состояние benchmark на дату.

Модель данных не должна зависеть от формата конкретного XLSX.

---

# 25. Data lineage

Для каждого показателя должна быть возможность определить:

- источник;
- дату;
- исходный файл/API;
- исходное поле;
- преобразование;
- benchmark-группу, на которой выполнен расчёт.

Это необходимо для проверки результатов и последующей отладки.

Пользователю необязательно видеть это на главном экране.

---

# 26. Требования к импорту

Импорт должен:

- определять тип поддерживаемого отчёта;
- валидировать структуру;
- нормализовать данные;
- не принимать молча некорректные строки;
- показывать количество импортированных/пропущенных записей;
- сохранять исходный snapshot;
- предотвращать неконтролируемые дубли.

Ошибка одной строки не должна блокировать весь импорт, если остальные данные валидны.

---

# 27. Архитектурный принцип источников

Аналитическое ядро не должно знать, пришли данные из:

- XLSX;
- официального Seller API;
- Performance API;
- внутреннего API Ozon;
- MPStats.

Источник должен преобразовывать данные в единую внутреннюю модель.

То есть:

**Source Adapter → Normalized Domain Model → Analytics Engine → UI**

Это обязательное требование, чтобы после появления/API-исследования не переписывать аналитику.

---

# 28. Что система не должна делать в первой версии

Не требуется:

- автоматически менять рекламные ставки;
- автоматически запускать или отключать рекламу;
- гарантировать позицию по заданной ставке;
- утверждать внутреннюю формулу ранжирования Ozon;
- использовать MPStats-продажи как benchmark при наличии данных Ozon;
- строить универсальный рейтинг карточки 0–100;
- автоматически менять контент карточки;
- автоматически выбирать конкурентов без подтверждения пользователя;
- делать большое количество BI-графиков;
- строить причинные выводы там, где есть только корреляционные данные.

---

# 29. UX-принципы

Приоритет интерфейса:

**диагноз > показатель > детализация.**

На каждом экране пользователь сначала должен видеть ответ, а уже затем исходную аналитику.

Не показывать одновременно несколько способов выразить одно отклонение.

Основное представление:

> Наше значение → benchmark → Δ → статус.

P25/P75, распределения и исходные строки конкурентов доступны в детализации.

Главный экран карточки не должен требовать горизонтальной прокрутки.

Heatmap кластеров должна помещать основные пять факторов без дополнительных колонок.

---

# 30. Целевой пользовательский сценарий

Пользователь открывает товар.

Система сообщает:

> Продажи на 38% ниже benchmark.

Далее:

> Главная причина — недостаточная видимость. Показы на 55% ниже benchmark, при этом конверсия находится на нормальном уровне.

Пользователь открывает поисковую диагностику.

Выбирает запрос.

Система показывает:

> Популярность ниже benchmark практически во всех кластерах.  
> В Москве дополнительно проигрываем по доставке.  
> Релевантность находится около benchmark.

Пользователь открывает «Разгон».

Система сообщает:

> Текущая CR нормальна для позиции 60–90. Низкая абсолютная конверсия преимущественно объясняется местом в выдаче. Товар является кандидатом на тест разгона.

После накопления истории:

> Для удержания TOP-10 раньше требовалась ставка около 200 ₽, сейчас около 120 ₽. Товар показывает признаки закрепления.

Это является целевым результатом продукта.

---

# 31. Definition of Done продукта

Базовая версия системы считается функционально состоявшейся, когда пользователь может:

1. Загрузить поддерживаемые данные Ozon.
2. Выбрать собственный SKU.
3. Получить кандидатов в конкуренты.
4. Увидеть их основные фотографии.
5. Сформировать и сохранить benchmark-группу.
6. Получить общий benchmark карточки.
7. Увидеть автоматический диагноз основных причин отставания.
8. Выбрать поисковый запрос.
9. Получить heatmap по кластерам.
10. Раскрыть исходные показатели выбранных конкурентов.
11. Накапливать snapshots во времени.
12. Открыть отдельный режим «Разгон».
13. Сравнить свою CR с benchmark CR для сопоставимой позиции.
14. Получить вердикт «разгонять / сначала чинить карточку / разгон не нужен».
15. При достаточной истории увидеть оценочные сценарии TOP-20 / TOP-10 / TOP-3.
16. При достаточной истории отслеживать снижение или рост требуемой ставки для удержания позиции.
17. Заменить XLSX-источник на API-адаптер без переписывания аналитического ядра.

---

# 32. Главный критерий качества

Система считается удачной не тогда, когда она показывает максимум доступных данных Ozon, а когда по карточке можно быстро ответить на четыре вопроса:

**1. Где мы проигрываем?**  
**2. Почему мы проигрываем?**  
**3. Это системная проблема или проблема конкретного запроса/кластера?**  
**4. Низкая конверсия вызвана самой карточкой или её текущим местом в выдаче?**

Все функции, которые не помогают ответить хотя бы на один из этих вопросов, не должны усложнять основной интерфейс.
