# ТЗ — система диагностики и benchmark-аналитики карточек Ozon

**Статус:** каноническая продуктовая спецификация  
**Репозиторий:** `vgvolmax/SCOZ`

## 1. Назначение системы

Разработать внутреннее аналитическое приложение для оценки собственных карточек Ozon относительно **выбранной пользователем группы реальных прямых конкурентов**.

SCOZ отвечает на два разных бизнес-вопроса.

### Режим «Диагностика»

> Где наша карточка проигрывает выбранным конкурентам и чем это объясняется?

Логика исследования:

> результат → трафик → конверсия → поисковая видимость → факторы ранжирования → конкретные запросы и кластеры.

### Режим «Разгон»

> Низкая конверсия действительно говорит о слабой карточке или соответствует низкой позиции в выдаче? Есть ли смысл временно покупать более высокую позицию рекламой и затем снижать ставку по мере закрепления товара?

Оба режима используют общую историческую базу, но остаются разными пользовательскими сценариями.

---

## 2. Продуктовый принцип

SCOZ не должен превращаться в BI-панель с десятками KPI.

Основной порядок представления:

> **ответ → причина → подтверждающие показатели → исходные данные.**

Пользователь выбирает свой SKU, видит главный диагноз, а затем при необходимости проваливается в запросы, кластеры, benchmark details и «Разгон».

На основном уровне не показывать одновременно все поля Ozon, P25/P75, технический provenance и длинные тексты.

Не создавать универсальный рейтинг карточки 0–100.

---

## 3. Источники данных

Архитектура источников должна быть заменяемой: XLSX сегодня может быть заменён официальным API завтра без переписывания аналитического ядра.

### 3.1. Ozon — «Товары на Ozon»

Основной источник конкурентных товарных показателей.

Хранить доступные поля максимально полно, включая при наличии:

- продажи, шт.;
- выручку;
- показы;
- поиск/каталог;
- просмотры карточки;
- конверсии;
- добавления в корзину;
- цену;
- остатки/доступность;
- total DRR;
- рекламные и вспомогательные показатели.

Не все поля обязаны отображаться пользователю.

### 3.2. Ozon — «Что влияет на место»

Источник уровня:

> **SKU × search query × cluster × observation**

Хранить при наличии:

- позицию;
- сводную оценку Ozon;
- релевантность;
- популярность;
- продвижение;
- CPC/CPO;
- доставку;
- цену/индекс цены;
- рейтинг/отзывы;
- другие факторы отчёта.

На основном экране используется только ограниченный набор факторов; остальные доступны в drill-down.

### 3.3. Ozon — аналитика собственного товара / поисковые запросы

Для own SKU сохранять доступную историю:

- поисковых запросов;
- видимости/показов;
- позиции;
- переходов;
- конверсий;
- заказов/оборота;
- других source metrics.

Гранулярность сохраняется максимально близко к source.

### 3.4. Ozon — метрики поисковых запросов

Используются для Query Demand/Query Quality: частотность/популярность, CR рынка, доля без действий, заказы/оборот и другие доступные query-level metrics.

### 3.5. Ozon Performance API

Используется только для собственных товаров/кампаний и нужен режиму «Разгон» для наблюдаемой рекламной истории.

### 3.6. MPStats

MPStats используется ограниченно:

- главные фотографии кандидатов для ручного отбора прямых конкурентов;
- история позиций own SKU и выбранных competitors по поисковым запросам.

MPStats sales estimates не являются основным числовым benchmark при наличии Ozon data.

### 3.7. Допустимая автоматизация Ozon

Использовать только официально разрешённые public API и пользовательские экспортируемые файлы.

Undocumented/internal API, `xapi`, Selenium/WebDriver и автоматический парсинг кабинета не входят в продуктовый план.

---

## 4. Модель конкурентов

Benchmark нельзя считать по всей выдаче Ozon.

Для каждого собственного SKU пользователь формирует и сохраняет benchmark-группу прямых конкурентов.

Кандидаты собираются по релевантным поисковым запросам. Для отбора показываются при наличии:

- главное фото;
- название;
- SKU;
- бренд;
- цена;
- ключевые характеристики.

Пользователь вручную включает только реально сопоставимые товары.

Benchmark рассчитывается **только по выбранным competitor SKU**.

Изменение группы запускает пересчёт аналитики и сохраняет новую версию состава, чтобы исторический результат оставался воспроизводимым.

---

## 5. Общая математическая модель benchmark

Базовый benchmark показателя:

> **медиана выбранных конкурентов.**

Дополнительно рассчитываются при достаточной выборке:

- P25;
- P75;
- min/max при необходимости;
- sample size.

Основное представление:

> **Наш показатель | Benchmark | Δ | статус**

Для ratio metric допустимо:

`(own / benchmark - 1) × 100%`.

Для `lower is better` направление статуса инвертируется.

Не использовать arithmetic mean как основной benchmark.

---

## 6. Benchmark status и confidence

Нужно различать:

1. положение own SKU относительно competitors;
2. насколько надёжен сам benchmark.

При достаточной выборке базовая логика:

- на уровне/выше медианы — сильная зона;
- между P25 и медианой — промежуточная;
- ниже P25 — слабая.

Для `lower is better` логика инвертируется.

Если sample size недостаточен, числовые значения можно показывать, но статус не должен выглядеть статистически уверенным. Confidence возвращается отдельно.

Цвет всегда дублируется числом/текстом.

---

## 7. Режим «Диагностика»

Главный экран отвечает:

> Почему мы продаём хуже или лучше выбранных конкурентов?

Основной результат:

**Продажи, шт. → отклонение от benchmark**.

Далее показываются три диагностических контекста.

### Трафик

Главный показатель — показы/видимость.

### Конверсия

Главный показатель — показ → заказ.

Дополнительные при наличии:

- search/catalog → cart;
- card → cart.

### Оффер

Компактный контекст:

- цена относительно benchmark;
- доставка;
- рейтинг/отзывы;
- доступность/OOS, если влияет на интерпретацию.

На основном экране не более необходимого набора KPI.

---

## 8. Автоматическая диагностика

SCOZ должен не только показывать цифры, но и классифицировать структуру проблемы.

Минимальные типы:

- недостаток трафика;
- слабая конверсия;
- проблема внутри карточки;
- проблема выдачи;
- проблема оффера;
- комбинированный провал;
- высокая рекламная поддержка без сопоставимого результата;
- искажение периода ограниченной доступностью/OOS как confounder.

На основном экране — максимум **2–3 наиболее существенные причины**.

Не генерировать длинный общий аналитический текст.

Если OOS или маленькая выборка делают вывод ненадёжным, confidence снижается или сильный диагноз блокируется.

---

## 9. Benchmark рекламной интенсивности

Методика подробно фиксируется в `Дополнение к ТЗ — benchmark рекламной интенсивности.md`.

Базово:

```text
estimated promotion spend ≈ turnover × total DRR
ad support per sold unit = estimated promotion spend / ordered units
```

Сравнивать own SKU с медианой выбранных competitors.

Низкая рекламная интенсивность не считается автоматически лучшей. Её интерпретируют вместе с продажами, трафиком, позицией и популярностью.

CPC/CPO и дополнительные рекламные fields — drill-down/context, а не отдельный advertising BI.

---

## 10. Поисковая видимость

Основная гранулярность:

> **SKU × query × cluster**

Пользователь сначала выбирает query, затем видит heatmap по кластерам.

Основная таблица:

| Кластер | Позиция | Релевантность | Популярность | Доставка | Цена |
|---|---:|---:|---:|---:|---:|

Каждый factor оценивается относительно валидных members benchmark-группы для того же query/cluster observation.

Отсутствующее observation не превращается в `0`.

Сводная оценка Ozon, CPC/CPO, рейтинг, отзывы и дополнительные factors хранятся и доступны в детализации, но не перегружают heatmap.

### Все кластеры

Если есть надёжные weights demand/traffic — допускается weighted aggregation. Если нет — показывать явный unweighted mode, а не создавать ложную точность.

---

## 11. Query Opportunity

Методика подробно фиксируется в `Дополнение к ТЗ — Query Opportunity Benchmark.md`.

Query Opportunity — не отдельный глобальный dashboard. Это слой приоритизации перед кластерной heatmap и вход для режима «Разгон».

Четыре смысловых блока:

- Query Demand;
- Query Quality;
- Visibility Gap;
- Position Stability.

Не создавать непрозрачный Opportunity Score 0–100 в v1.

Рыночная CR query не является CR конкретного competitor SKU.

Share of Top рассчитывается только по наблюдениям с подтверждённой date/null semantics и всегда показывает denominator/sample size.

---

## 12. Режим «Разгон»

Главный вопрос:

> Нормальна ли наша CR для текущего уровня позиции и есть ли смысл покупать более высокое место?

### 12.1. Position-normalized conversion

Нельзя сравнивать aggregate own/competitor CR без учёта позиции.

Система строит эмпирическую зависимость `position → typical conversion` только на данных с совместимой гранулярностью.

Базовые configurable position buckets:

- 1–3;
- 4–10;
- 11–20;
- 21–50;
- 51–100;
- 100+.

Если данных недостаточно, модель не строится.

### 12.2. Общая granularity

Ramp-up работает на **максимально детальной общей granularity**, реально присутствующей у необходимых входов.

Базовый практический уровень:

> **SKU × query × time**

Cluster добавляется только если position, conversion evidence и advertising inputs действительно доступны на совместимом cluster level.

Нельзя искусственно размножать query-level values по кластерам.

### 12.3. Cross-sectional vs longitudinal

Cross-sectional observations competitors дают ориентир рынка.

Longitudinal history одного SKU при достаточном объёме имеет большую ценность для оценки именно этого SKU.

Aggregate competitor CR из «Товары на Ozon» нельзя объявлять query-position CR.

---

## 13. Вердикт «Разгона»

Центральные состояния:

| Позиция | CR относительно сопоставимой позиции | Вывод |
|---|---|---|
| Низкая | Нормальная | Кандидат на разгон |
| Низкая | Плохая | Сначала улучшить карточку/оффер |
| Высокая | Нормальная | Дополнительный разгон не требуется |
| Высокая | Плохая | Проблема карточки/оффера |

Дополнительное состояние:

> **Недостаточно данных**.

Query Opportunity влияет на решение: слабый коммерческий query не становится приоритетом только из-за низкой позиции.

---

## 14. Сценарии и organic support

При достаточной истории показывать:

- Сейчас;
- TOP-20;
- TOP-10;
- TOP-3.

Для scenario допускаются диапазоны ожидаемой позиции, CR и ставки + confidence.

Запрещена псевдоточная гарантия позиции по ставке.

«Органическая опора» — рабочий аналитический термин, не утверждение внутренней формулы Ozon.

Практический сигнал:

> для удержания сопоставимой TOP-N позиции со временем требуется меньшая рекламная ставка.

Тренд строится только на сопоставимых observations.

---

## 15. История и воспроизводимость

История является обязательной с первого этапа.

Новый period/date не перезаписывает старое observation.

Если source исправил данные за тот же logical period, новая версия сохраняется как revision, а предыдущая остаётся для аудита и не должна повторно участвовать в расчёте как отдельное observation.

Состав benchmark-группы также versioned.

Для результата должно быть возможно определить:

- source;
- period/date;
- исходный artifact/API response;
- normalized observation/revision;
- benchmark revision;
- calculation/model version;
- sample/confidence.

---

## 16. Работа с недостаточными/несопоставимыми данными

Система не должна выдавать сильный вывод при маленькой выборке или несовместимых periods/granularity.

Минимальные confidence states:

- высокая;
- средняя;
- данных недостаточно.

Thresholds задаются analytics config, не UI.

Daily position нельзя молча связывать row-by-row с 28-day CR. Query-level data нельзя превращать в cluster-level. Missing observation нельзя заменять нулём.

---

## 17. Импорт

Импорт должен:

- определить поддерживаемый report type;
- проверить schema;
- нормализовать data;
- не принимать молча некорректные rows;
- показать imported/skipped/errors;
- сохранить raw artifact/provenance;
- предотвратить uncontrolled duplicates;
- корректно обработать revised report за тот же logical period.

Ошибка отдельной строки не должна блокировать безопасно импортируемые валидные строки. Structural ambiguity блокирует импорт всего файла.

---

## 18. Что не входит в первую версию

Не требуется:

- автоматически менять/включать/выключать рекламные ставки;
- гарантировать позицию;
- утверждать внутреннюю формулу ранжирования Ozon;
- использовать undocumented Ozon automation;
- автоматически выбирать competitors без подтверждения пользователя;
- автоматически менять content карточки;
- использовать MPStats sales estimates как основной benchmark при наличии Ozon data;
- восстанавливать competitor ad/organic sales;
- считать seller price/СПП-подобные показатели;
- строить универсальный score карточки 0–100;
- строить Opportunity Score 0–100;
- создавать отдельный advertising BI;
- перегружать продукт большим количеством графиков.

---

## 19. Целевой пользовательский сценарий

Пользователь открывает own SKU и получает короткий диагноз относительно выбранных competitors.

Если проблема в поисковой видимости, система показывает приоритетные queries, затем query×cluster heatmap и конкретные факторы разрыва.

В режиме «Разгон» SCOZ сообщает, соответствует ли CR текущей позиции, является ли query подходящим для эксперимента и, при достаточной истории, показывает диапазонные сценарии и динамику organic support.

Пользователь всегда может раскрыть source/benchmark details, но основной экран остаётся простым.

---

## 20. Definition of Done продукта

Базовая версия функционально состоялась, когда пользователь может загрузить поддерживаемые Ozon data, выбрать own SKU, сформировать benchmark-группу по фотографиям кандидатов, получить общий benchmark и автоматический диагноз, выбрать ценный query, увидеть cluster heatmap и исходные competitor values, накопить историю, открыть режим «Разгон», получить честный verdict/confidence и при достаточной истории увидеть TOP-сценарии и organic-support trend.

Замена XLSX на официальный API для поддерживаемого data flow не должна требовать переписывания analytics/UI.

---

## 21. Главный критерий качества

SCOZ считается удачным, если по карточке можно быстро ответить:

1. Где мы проигрываем?
2. Почему мы проигрываем?
3. Это системная проблема или конкретный query/cluster?
4. Низкая CR вызвана карточкой или текущим местом?
5. Если место — по какому query действительно есть смысл пытаться расти?

Функции, не помогающие принять эти решения, не должны усложнять основной интерфейс.
